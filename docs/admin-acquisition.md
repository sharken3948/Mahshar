# Admin acquisition review mode

`ADMIN_ACQUISITION_MODE=true` selects the acquisition Workflow branch behind the existing Admin Worker Start, Stop and Resume routes. The default remains the bounded Discovery Worker. The required acquisition migrations are installed in Production. Deployment alone does not start the Worker. The deterministic acquisition canary, continuous Worker, and Groq-backed qualification are distinct operations.

Each discovery chunk finishes official research and qualification before the acquisition coordinator processes up to ten providers sequentially. The coordinator records an investigation per provider. An observed public email, a syntactically valid email, verified official contact evidence, recipient eligibility, and channel approval are separate conditions. No eligibility record is created by discovery. Existing provider Outreach threads and rejection or Do Not Contact decisions block a reservation.

The canary dispatch adapter returns a `simulated:` ID and never calls Brevo or another external service. Mock eligibility uses the separate expiring `channel='mock'` authorization. Mock reservations and IDs remain solely in acquisition attempts and cannot be approved or sent through Admin Outreach. Continuous operation prepares immutable drafts without requiring sending eligibility. Real delivery is a separate, disabled-by-default path described below; published email evidence never grants permission to send. Daily slots use UTC reservation time; simulated dispatches use UTC dispatch time.

The Workflow starts the next eligible discovery run immediately after completion while the acquisition intent remains running. A run can last up to 60 minutes. Its continuation RPC caps autonomous discovery runs at 20 per UTC day; application Start and Resume checks use the same limit. An exhausted daily cap or empty run stops the continuous intent instead of polling. Existing daily usage is retained. Stop clears acquisition intent before requesting the existing Worker stop. Resume uses the saved Worker checkpoint when one exists; after a completed batch it starts the next discovery run while retaining provider history.

## Controlled Production canary

Acquisition Start requires `ADMIN_ACQUISITION_MODE=true` and exactly one separately approved mode: `ADMIN_ACQUISITION_CANARY=true` or `ADMIN_ACQUISITION_CONTINUOUS=true`. All flags default to false. Setting both operating modes is rejected before a run is created. The canary consumes one durable session in `admin_acquisition_control`; it cannot be started or resumed again after that session is used. Stop remains available while it runs. A failed launch also consumes the session, so an operator must review the state rather than retry automatically.

The canary uses one existing researched Worker lead and its official contact evidence. It performs no new discovery fetch or qualification, makes no Groq request, investigates at most one provider, and uses a deterministic mock draft with the evidenced API product. The existing mock dispatch adapter records a `simulated:` result only in the acquisition attempt. The Workflow stops the acquisition intent and Worker run after this single pass, with no durable sleep or continuation. Database claim and continuation RPCs enforce the same one-provider and no-continuation bounds. If no due lead or mock-eligible recipient exists, the session ends without a draft or simulated delivery; do not edit prior provider records or bypass eligibility to force a result.

## Continuous draft preparation

The additive `20261014000600_admin_acquisition_continuous.sql` migration and matching application are deployed. Acquisition flags default to disabled. Continuous operation requires explicit operator approval, `ADMIN_ACQUISITION_MODE=true`, `ADMIN_ACQUISITION_CONTINUOUS=true`, and `ADMIN_ACQUISITION_CANARY=false`; Admin Start remains a separate action. Switching mode preserves the original canary run ID, usage timestamp and all provider attempts. The consumed canary stays consumed.

Continuous operation reuses existing discovery, official research, contact checks and qualification AI. Each provider is processed sequentially and acquisition is drained after its research before advancing. With `20261015000400_admin_invitation_name_integrity.sql`, invitation version `mahshar-provider-invitation-v2` uses explicit official naming evidence, without invitation inference or extra fetches. Existing official HTML research fetches may save bounded body statements or typed schema.org Organization/Product/SoftwareApplication/WebAPI/Service metadata as supplemental evidence. Directory titles, OpenAPI info.title, Swagger headings, page titles and domain labels never establish company or commercial product names. Missing, conflicting, stale or rejected naming proof yields `Hello team,` and/or the exact safe sentence `We'd like to invite your team to explore listing one of your APIs on Mahshar.` API and Developer are allowed in legitimate product names; documentation, portal, demo, sandbox, test and environment labels fail closed. Current identity/contact evidence, qualification, existing suppression/history checks and fenced saves remain required. Database and application validation check the exact final approved subject/body. Immutable drafts include their version and full naming-proof snapshot. Existing v1/Groq drafts and evidence are not backfilled or rewritten; Admin counts and View retain both template versions.

Initial Outreach reservation and the final Brevo adapter independently call the same service-only naming assertion. Historical approval cannot bypass it: an initial invitation must exactly match approved generic wording or use currently verified names. Safe generic wording remains valid when better evidence later appears. The final assertion checks the exact persisted recipient/subject/body, approval, reservation and uncertainty before transport. Old unsafe bodies are rejected, never silently repaired. Replies retain their existing sender/authorization review, and existing approval, DNC, recipient eligibility, duplicate and delivery authorization checks remain unchanged. Draft preparation grants no sending permission, creates no reservation or sendable Outreach record, and does not activate Brevo.

Preparation claims have a fenced 15-minute lease. Safe pre-dispatch skips are reconsidered once when adopting the versioned standard template, then only when relevant contact, identity or template-variable evidence changes. Timestamp-only rechecks do not trigger another investigation. Prior skip reasons, original timestamps and run/lead associations are archived before reconsideration and displayed separately from current contact readiness. Saved drafts, legacy text, reservations, uncertain attempts, prior outreach and suppression are never automatically reclaimed. A saved `prepared` checkpoint is reused by excluding it from further claims, including after a lost save response. Daily ceilings remain 20 discovery runs, at most 100 Groq calls per run and 25 UTC reservation slots; draft-only preparation consumes no reservation slot. Cloud continuation and Worker controls are unchanged. The additive migration and matching application are deployed; flags and Admin Start still control execution.

Temporary official-document/ownership failures use existing durable deferred candidates and leases: at most three retries with 1, 2 and 4 hour backoff. Exhausted retries remain visible and researchable for manual review. Stop clears the epoch intent before requesting Worker stop; new research requests, inference, provider claims, reservations and continuation are gated by current intent. Already dispatched requests may finish and persist their results. Workflow replay of a completed batch continues from its idempotent child run rather than reprocessing its parent. A terminal infrastructure failure stops the epoch; Admin Resume uses the saved checkpoint and provider history.

The panel distinguishes acquisition totals, pending investigations, exhausted research retries and cloud continuation state from legacy discovery progress. Continuous invitations use the approved versioned template; qualification AI is unchanged. The dashboard counts validated saved template and historical Groq drafts separately. Offline validation makes no inference requests. Without explicit Brevo activation and database authorization, continuous operation creates only immutable drafts. Keep Brevo deactivated and inbound reply automation paused during review.

## Brevo acquisition delivery (disabled by default)

The installed additive migration `20261015000600_admin_acquisition_brevo_delivery.sql` preserves existing rows, drafts, Worker controls, acquisition flags and delivery history. It creates one disabled channel-control row and no Brevo recipient permissions. The matching application is deployed, but the channel and Worker remain inactive without separate authorization.

Future activation requires all of the following, under a separately authorized operational change:

- A verified, active Brevo account and authenticated `support@mahshar.xyz` sender/domain, including required SPF/DKIM/DMARC configuration and a usable `BREVO_API_KEY` in the intended Production environment.
- An explicitly approved `ADMIN_ACQUISITION_BREVO_ENABLED=true`, `ADMIN_ACQUISITION_MODE=true`, `ADMIN_ACQUISITION_CONTINUOUS=true`, canary disabled, and `MAINNET_MODE=true`. The new flag defaults to false. Existing Admin Start/Stop/Resume controls remain separate.
- A reviewed `admin_acquisition_delivery_control` authorization with sender verification, policy review reference, reviewer wallet and expiry no more than 30 days after review. Runtime service access is SELECT only; neither discovery nor the Admin APIs can activate it.
- A separate, unexpired `admin_acquisition_eligibility` record for the exact provider/recipient and `channel='brevo'`, with explicit consent or a requested invitation, permission evidence reference, reviewer and review time. Its expiry is also bounded to 30 days. Mock authorization is never real-send authorization. Officially published contact information alone is insufficient.

Brevo's [contact policy](https://help.brevo.com/hc/en-us/articles/213405965-Build-a-legitimate-contacts-database-for-optimal-deliverability-and-compliance) and [anti-spam policy](https://help.brevo.com/hc/en-us/articles/209405205-What-is-the-anti-spam-policy-of-Brevo) must be satisfied for the particular recipients and purpose. This integration does not authorize invitations to scraped addresses. Account deactivation, sender configuration and permission proof remain operator activation requirements.

After each bounded draft-preparation batch, the optional delivery stage claims at most that batch's provider limit. Only successfully saved V2 template drafts with current verified identity/contact evidence, safe current official naming or approved generic wording, permission and no prior Outreach are candidates. The claim creates a separate immutable-content Outreach message linked to the original draft, using the recorded recipient reviewer as its approval provenance, then calls the existing provider-level reservation. DNC, suppression, provider history, recipient verification and Product Name Integrity V2 still apply. Original Acquisition drafts and historical Groq/simulated records are never overwritten or upgraded to sent.

Immediately before HTTP, a service-only boundary rechecks the exact saved payload, current naming/contact/suppression, channel and recipient approval, active epoch, Worker intent, run deadline and provider history. It atomically consumes a permanent one-shot dispatch marker. Only the winning caller can use the existing Brevo plain-text transport. The HTTP request carries the stable Outreach UUID as its idempotency key, but duplicate prevention does not depend on Brevo's temporary idempotency retention. The unchanged daily ceiling of 25 slots now counts mock and real reservations together, including failures and uncertain outcomes. Research, qualification, Groq, daily run and other batch budgets are unchanged.

A valid HTTP 201 receipt records acceptance through the existing idempotent Outreach completion RPC and delivery-event pipeline; acceptance is not proof of delivery. Receipt persistence may retry once with the same receipt, without repeating HTTP. Recognized explicit provider rejections save a bounded failure code and retain the reservation. Network errors, timeouts, unknown/duplicate responses, malformed receipts and server errors are uncertain. Reservations, dispatch markers and uncertainty remain barriers across crashes and Workflow replay; there is no automatic real-send retry, including after a rejection. Lost claim or final-gate responses fail closed. Review and reconcile these records rather than clearing reservations or resending them.

Admin Worker View shows the immutable prepared draft separately from the linked Brevo record and its template version, acceptance, delivery events, rejection or uncertainty. Simulations remain explicitly labeled and excluded from real sent counters. Admin Outreach retains its existing controls and cannot resend an already reserved Acquisition message. No new public endpoint or activation UI is added. Before eventual release/activation, verify the intended database/environment through the established secure workflow; no local environment file alone establishes the Production target.
