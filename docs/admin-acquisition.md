# Admin acquisition review mode

`ADMIN_ACQUISITION_MODE=true` selects the autonomous Workflow branch behind the existing Admin Worker Start, Stop and Resume routes. The default remains the existing bounded Discovery Worker. The migration `20261014000100_admin_acquisition.sql` must be applied before enabling this mode.

Each discovery chunk finishes official research and qualification before the acquisition coordinator processes up to ten providers sequentially. The coordinator records an investigation per provider. An observed public email, a syntactically valid email, verified official contact evidence, recipient eligibility, and channel approval are separate conditions. No eligibility record is created by discovery. Existing provider Outreach threads and rejection or Do Not Contact decisions block a reservation.

The only autonomous dispatch adapter returns a `simulated:` ID and never calls Brevo or another external service. An eligibility row permits only `channel='mock'` and expires. A successful atomic reservation stores the draft solely in the acquisition attempt; it creates no ordinary Outreach thread or message. The mock ID remains solely in the acquisition attempt and cannot be approved or sent through Admin Outreach. Reserved and uncertain attempts remain unique by provider and are never retried automatically. Daily slots use UTC reservation time; simulated dispatches use UTC dispatch time.

The Workflow sleeps durably for one hour between bounded discovery runs and starts the next run only while the acquisition intent remains running. Its continuation RPC caps autonomous discovery runs at six per UTC day. Stop clears acquisition intent before requesting the existing Worker stop. Resume uses the saved Worker checkpoint when one exists; after a completed batch it starts the next discovery run while retaining provider history.

## Controlled Production canary

Acquisition Start requires `ADMIN_ACQUISITION_MODE=true` and exactly one separately approved mode: `ADMIN_ACQUISITION_CANARY=true` or `ADMIN_ACQUISITION_CONTINUOUS=true`. All flags default to false. Setting both operating modes is rejected before a run is created. The canary consumes one durable session in `admin_acquisition_control`; it cannot be started or resumed again after that session is used. Stop remains available while it runs. A failed launch also consumes the session, so an operator must review the state rather than retry automatically.

The canary uses one existing researched Worker lead and its official contact evidence. It performs no new discovery fetch or qualification, makes no Groq request, investigates at most one provider, and uses a deterministic mock draft with the evidenced API product. The existing mock dispatch adapter records a `simulated:` result only in the acquisition attempt. The Workflow stops the acquisition intent and Worker run after this single pass, with no durable sleep or continuation. Database claim and continuation RPCs enforce the same one-provider and no-continuation bounds. If no due lead or mock-eligible recipient exists, the session ends without a draft or simulated delivery; do not edit prior provider records or bypass eligibility to force a result.

## Continuous simulated acquisition (requires separate release and approval)

Apply the additive `20261014000600_admin_acquisition_continuous.sql` migration after the four security remediations, then deploy reviewed code with all acquisition flags disabled. Continuous operation requires explicit operator approval, `ADMIN_ACQUISITION_MODE=true`, `ADMIN_ACQUISITION_CONTINUOUS=true`, and `ADMIN_ACQUISITION_CANARY=false`; Admin Start remains a separate action. Switching mode preserves the original canary run ID, usage timestamp and all provider attempts. The consumed canary stays consumed.

Continuous operation reuses existing discovery, official research, contact checks and qualification AI. Each provider is processed sequentially and acquisition is drained after its research before advancing. With `20261015000400_admin_invitation_name_integrity.sql`, invitation version `mahshar-provider-invitation-v2` uses explicit official naming evidence, without invitation inference or extra fetches. Existing official HTML research fetches may save bounded body statements or typed schema.org Organization/Product/SoftwareApplication/WebAPI/Service metadata as supplemental evidence. Directory titles, OpenAPI info.title, Swagger headings, page titles and domain labels never establish company or commercial product names. Missing, conflicting, stale or rejected naming proof yields `Hello team,` and/or the exact safe sentence `We'd like to invite your team to explore listing one of your APIs on Mahshar.` API and Developer are allowed in legitimate product names; documentation, portal, demo, sandbox, test and environment labels fail closed. Current identity/contact evidence, qualification, existing suppression/history checks and fenced saves remain required. Database and application validation check the exact final approved subject/body. Immutable drafts include their version and full naming-proof snapshot. Existing v1/Groq drafts and evidence are not backfilled or rewritten; Admin counts and View retain both template versions.

Initial Outreach reservation and the final Brevo adapter independently call the same service-only naming assertion. Historical approval cannot bypass it: an initial invitation must exactly match approved generic wording or use currently verified names. Safe generic wording remains valid when better evidence later appears. The final assertion checks the exact persisted recipient/subject/body, approval, reservation and uncertainty before transport. Old unsafe bodies are rejected, never silently repaired. Replies retain their existing sender/authorization review, and existing approval, DNC, recipient eligibility, duplicate and delivery authorization checks remain unchanged. Draft preparation grants no sending permission, creates no reservation or sendable Outreach record, and does not activate Brevo.

Preparation claims have a fenced 15-minute lease. Safe pre-dispatch skips are reconsidered once when adopting the versioned standard template, then only when relevant contact, identity or template-variable evidence changes. Timestamp-only rechecks do not trigger another investigation. Prior skip reasons, original timestamps and run/lead associations are archived before reconsideration and displayed separately from current contact readiness. Saved drafts, legacy text, reservations, uncertain attempts, prior outreach and suppression are never automatically reclaimed. A saved `prepared` checkpoint is reused by excluding it from further claims, including after a lost save response. Daily ceilings remain six discovery runs, at most 100 Groq calls per run and 25 UTC reservation slots; draft-only preparation consumes no reservation slot. Cloud continuation and Worker controls are unchanged. Apply the additive migration separately before releasing the matching code; this local change does not activate flags or start the Worker.

Temporary official-document/ownership failures use existing durable deferred candidates and leases: at most three retries with 1, 2 and 4 hour backoff. Exhausted retries remain visible and researchable for manual review. Stop clears the epoch intent before requesting Worker stop; new research requests, inference, provider claims, reservations and continuation are gated by current intent. Already dispatched requests may finish and persist their results. Workflow replay of a completed batch continues from its idempotent child run rather than reprocessing its parent. A terminal infrastructure failure stops the epoch; Admin Resume uses the saved checkpoint and provider history.

The panel distinguishes acquisition totals, pending investigations, exhausted research retries and cloud wait state from legacy discovery progress. Continuous invitations use the approved versioned template; qualification AI is unchanged. The dashboard counts validated saved template and historical Groq drafts separately. Offline validation makes no inference requests. Outbound delivery remains entirely simulated, creates no sendable Admin Outreach record and has no live transport switch. Keep Brevo deactivated and inbound reply automation paused.

Before enabling either flag, the operator must confirm in the secure Vercel and Supabase consoles that the linked Production environment points to the intended Production database. A local `.env.local` target is insufficient evidence when the Vercel CLI returns encrypted placeholders. Review the migration, existing Worker status, candidate and eligibility readiness, sender configuration, quotas, and the intended mock message. Apply the migration separately, deploy code with both flags false, then obtain explicit approval before enabling both flags in Production. Do not configure a live acquisition transport. To stop or roll back, press Admin Stop first, verify acquisition intent is stopped, then disable both flags and redeploy the previous code if needed. Leave the additive migration and historical attempts in place.

Before any real sending can be designed, an operator must review the sender, legal and sending-provider requirements, recipient eligibility evidence, quotas and message samples. Brevo's transactional API is not an approved channel for promotional invitations to publicly discovered addresses. A separate approved channel and an explicit activation change with end-to-end verification would be required. This mode offers no live-send switch.
